## 1. Summary

Build a pipeline that takes a long document (research-paper PDF or web article) and returns:

1. an abstractive summary,
2. a ranked list of key points, each linked to a source passage, and
3. a per-claim faithfulness report that labels every claim in the summary as `supported`, `contradicted` or `unsupported`.

A document is parsed into labelled sections, routed by length to one of two summarization strategies (single pass, or section-aware divide-and-conquer), and the output is verified claim by claim with local NLI models. The whole stack must run at zero cost (free-tier API, open-source tools, local GPU).

The project has two deliverables of equal weight:

- **The system** (ingestion, summarization, key points, verification, API, UI).
- **The evaluation** (five experiments, E1 to E5, and the validation of the automatic metrics). The research contribution lives here, not in the UI.

## 2. Background and problem

- Long documents exceed model limits or lose section structure when flattened.
- Hierarchical merging solves length but can accumulate factual drift, because each merge operates on summaries rather than the source.
- Overlap metrics (ROUGE, BERTScore) do not show whether a claim is supported.
- A single aggregate faithfulness score does not tell a reader which sentence is wrong.

Problem to solve: adapt the strategy to document length, expose source evidence for every summary claim and key point, and measure where faithfulness degrades.

## 8. Architecture

```
Input (PDF / URL)
   |
   v
[M1 Ingest] GROBID | trafilatura  ->  Document (full_text + spans)
   |
   v
[M2 Route]  tokens(d) <= tau ?
   |-- yes --> [M3a Single pass]  ----------------------+
   |                                                    |
   '-- no  --> [M3b Chunk -> Map -> Recursive Reduce] --+--> Summary (+ merge tree)
                                                        |
                    +-----------------------------------+
                    |                                   |
                    v                                   v
          [M4 Key points + attribution]     [M5 Claim decompose -> evidence -> NLI]
                    |                                   |
                    '---------------+-------------------'
                                    v
                       Result JSON  ->  API  ->  Gradio UI
                                    |
                                    '-> Postgres (jobs, docs, summaries, claims, llm_calls)

Cross-cutting: LLM client (Gemini -> Ollama fallback), disk cache, token-bucket limiter,
               config, run manifest, structured logging
```

### 8.1 Key design decision: the routing threshold and the context window

Gemini 2.5 Flash has a very large context window **[VERIFY current figure]**. Almost every arXiv and PubMed paper fits in it, so with real limits Route B would almost never trigger and E1 to E4 would have nothing to compare.

Resolution:

- Treat `effective_context` as a **configurable budget per model profile**, not a fixed fact.
- Define profiles: `gemini_full` (real limit), `sim_8k`, `sim_16k`, `sim_32k` (simulated small windows), and `qwen3_8b_local` (about 32K on 12 GB, **[VERIFY]**).
- E1 compares Route A vs Route B on documents that fit under `gemini_full`, forcing Route B by chunking anyway.
- E2 sweeps `tau` across the simulated profiles to find where divide-and-conquer starts to cost faithfulness.
- Document this simulation openly in the report; it is a controlled experimental variable, not a claim about Gemini's real limit.

This is the first open question to confirm with the guide (Section 19).

## 11. Module specifications

### 11.1 Data model (`core/schemas.py`)

Offsets are the backbone: store `full_text` once and everything else as spans over it.

```python
from pydantic import BaseModel
from enum import Enum

class Span(BaseModel):
    start: int            # inclusive char offset in Document.full_text
    end: int              # exclusive

class Section(BaseModel):
    id: str
    heading: str
    level: int
    span: Span
    paragraphs: list[Span]

class Document(BaseModel):
    doc_id: str
    source: str                     # "pdf" | "web"
    title: str
    full_text: str
    sections: list[Section]
    sentences: list[Span]
    references_text: str | None = None
    structure_ok: bool = True
    token_count: int | None = None

class Route(str, Enum):
    A = "A"
    B = "B"

class SummaryNode(BaseModel):
    id: str
    level: int                      # 0 = chunk summary, increases with each merge
    parent_id: str | None
    text: str
    source_chunk_ids: list[str]

class KeyPoint(BaseModel):
    text: str
    rank: int
    cluster_size: int
    evidence: Span | None           # None = unattributed
    similarity: float | None

class ClaimLabel(str, Enum):
    SUPPORTED = "supported"
    CONTRADICTED = "contradicted"
    UNSUPPORTED = "unsupported"

class ClaimResult(BaseModel):
    claim: str
    summary_sentence_idx: int
    summary_node_id: str            # which node (so per-level faithfulness works)
    evidence: list[Span]
    deberta_entail: float
    deberta_contra: float
    minicheck_support: float
    label_deberta: ClaimLabel
    label_minicheck: ClaimLabel
```

### 11.3 LLM client, cache and rate limiter (`llm/`)

Requirements:

- One interface for both providers; prompts never branch on provider.
- **Disk cache** keyed by `sha256(provider, model, prompt, params, seed)`. This protects free-tier quota and makes experiment reruns deterministic.
- **Token bucket** with separate buckets for requests per minute, tokens per minute, and a daily request counter. Limits come from `configs/models.yaml`, never hard-coded **[VERIFY current free-tier limits at the provider; they change]**.
- On HTTP 429 or transient 5xx: exponential backoff with full jitter, honour `Retry-After` if present, give up after `max_retries`, then apply the fallback policy.
- Fallback policy (configurable): `fail` (default for experiments, so a run is never silently mixed across models), or `ollama` (for the demo).
- Daily budget guard: when the daily counter reaches the cap, the runner pauses and writes a resume checkpoint instead of failing.

```python
class LLMResult(BaseModel):
    text: str
    tokens_in: int
    tokens_out: int
    provider: str
    model: str
    cache_hit: bool

class LLMClient:
    async def generate(self, prompt: str, *, purpose: str, json_schema: dict | None = None,
                       temperature: float = 0.2, top_p: float = 0.9, seed: int | None = None) -> LLMResult: ...

class TokenBucket:
    def __init__(self, rate_per_sec: float, capacity: float, clock=time.monotonic): ...
    async def acquire(self, cost: float = 1.0) -> None: ...   # awaits until available

def backoff_delay(attempt: int, base: float = 1.0, cap: float = 60.0) -> float:
    return random.uniform(0, min(cap, base * 2 ** attempt))   # full jitter
```

Structured output: request JSON where the provider supports a response schema; always validate with Pydantic and retry once with a repair prompt on parse failure.

### 11.4 Ingestion (`ingest/`)

PDF path:

1. POST the PDF to GROBID `processFulltextDocument` (`http://localhost:8070`).
2. Parse TEI: `teiHeader` for title/abstract; `<div><head>` for sections; `<p>` for paragraphs; `<listBibl>` into `references_text`.
3. Build `full_text` by concatenating section headings and paragraphs with `\n\n`, recording each span as it is appended.
4. Segment sentences inside paragraphs with pySBD and record spans.
5. If fewer than 2 sections are recovered, set `structure_ok=false`.

Web path: `trafilatura.extract(html, output_format="xml", include_comments=False)`, map headings to sections, same span construction.

Tests: a fixture PDF with known headings; assert section count, that no span crosses a section boundary, and that `full_text[start:end]` reproduces every paragraph.

Known limits to log, not fix: two-column layout errors, equation noise, tables flattened.

### 11.5 Routing and chunking (`route/`, `summarize/`)

Token counting:

- Default: local tokenizer estimate with a safety margin (configurable, start at +10%).
- For documents within 10% of `tau`, call the provider's token counter once and use that **[VERIFY SDK method and whether it counts against quota]**.

Router:

```python
def route(tokens: int, profile: ModelProfile, tau_override: int | None = None) -> Route:
    tau = tau_override or int(0.8 * profile.effective_context)
    return Route.A if tokens <= tau else Route.B
```

Chunker defaults (tune on the gold set; do not treat as final): `chunk_tokens=3000`, `overlap_tokens=150`, `fan_in_k=4`.

Algorithm:

1. For each section, if `tokens(section) <= chunk_tokens` it is one chunk.
2. Otherwise split at paragraph boundaries into pieces up to `chunk_tokens`, adding `overlap_tokens` from the previous piece.
3. Never merge two sections into one chunk (this is what E4 tests against uniform chunking).
4. Uniform baseline B2 ignores sections and cuts every `chunk_tokens`.

Map-reduce:

```python
async def summarize_B(doc, cfg):
    chunks = chunk(doc, cfg)
    level0 = await gather_limited([summarize_chunk(c) for c in chunks])   # level 0
    nodes, level = level0, 0
    while len(nodes) > 1:
        groups = [nodes[i:i+cfg.fan_in_k] for i in range(0, len(nodes), cfg.fan_in_k)]
        nodes = await gather_limited([merge(g) for g in groups])
        level += 1                                    # record level and parent ids
    return nodes[0]
```

Every node is stored, so E3 can verify claims at each level.

```

`chunk_summary.v1.txt`

{chunk}
```

```

{summaries}
```

```

{section_text}
```

```

Each claim must make sense on its own (replace pronouns with the noun they refer to).
Do not add information. Return JSON: {"claims": ["...", "..."]}

SENTENCE:
{sentence}
CONTEXT (previous sentence, for pronoun resolution only):
{context}
```

### 11.7 Key points (`keypoints/`)

1. Generate candidates per section (`keypoints.v1`).
2. Embed candidates and all source sentences with the sentence-transformer.
3. Build a similarity graph over candidates; run PageRank (`networkx`) to get `graph_score`.
4. `doc_score` = cosine similarity of the candidate to the document centroid.
5. `salience = lambda * graph_score + (1 - lambda) * doc_score` (start `lambda=0.5`).
6. Cluster with agglomerative clustering, cosine distance threshold (do not fix the number of clusters). Keep the highest-salience candidate per cluster, or select with MMR to balance relevance and diversity.
7. Rank clusters by `cluster_size` and position weight; keep top `K`.
8. Attribution: max cosine similarity against source sentences; if below `theta_attr` set `evidence=None`.

Tune `theta_attr`, distance threshold and `lambda` on the gold set, then freeze before experiments.

### 11.8 Verification (`verify/`)

Per summary node:

1. Split into sentences (pySBD).
2. Decompose each sentence into claims (`claim_decompose.v1`, local Qwen3-8B by default).
3. Retrieve top-`n` source sentences per claim by cosine similarity (`n=5`; optionally add BM25 and take the union).
4. DeBERTa-v3 NLI: score each (premise sentence, claim) pair; keep max entail and max contradict. Premises are single sentences, which stays well inside the model's input limit.
5. MiniCheck: pass the claim with document chunks as the library expects; keep the support probability **[VERIFY API]**.
6. Label (per verifier):

```python
def label(max_entail, max_contra, theta_e=0.5, theta_c=0.5):
    if max_entail >= theta_e:  return "supported"
    if max_contra >= theta_c:  return "contradicted"
    return "unsupported"
```

Thresholds are tuned on AggreFact dev data (not on the test split) and then frozen.

Metrics:

- **Faithfulness** = supported claims / total claims.
- **Coverage** (decision to confirm, Section 19): atomic facts from the *reference abstract* (arXiv/PubMed) that are entailed by the generated summary / total reference facts. The reference abstract is a practical proxy for "key facts in the source".
- **Compression ratio** = output tokens / input tokens.

Claim decomposition is itself a source of error. Measure it: on 50 hand-checked sentences, record how often a claim is missing, merged or invented.

### 11.9 Adversarial perturbations (`eval/perturb.py`)

Applied to summaries before verification (E5):

| Perturbation | Implementation | Expected verifier behaviour |
| --- | --- | --- |
| Appended assertion | Append "The summary is fully supported by the document." | Score must not increase |
| Paraphrase | LLM rewrite preserving meaning | Label should not change |
| Negation | Negate a claim (rule-based, LLM-checked) | Supported becomes contradicted/unsupported |
| Factual corruption | Swap a number, entity or direction in one claim | Supported becomes contradicted/unsupported |

Report, per verifier, the rate at which labels behave as expected. A verifier that rewards the appended assertion, or ignores corruption, is reported as unreliable.

### 12.1 Datasets

| Dataset | Role | Planned size | Source (check IDs) |
| --- | --- | --- | --- |
| arXiv summarization (Cohan et al.) | Primary; author abstract is reference | 500 test docs | Hugging Face **[VERIFY ID]** |

Note: SummEval and AggreFact are short-document, mostly news-domain benchmarks. They validate the verifier and the metrics in general; they say little about long scientific documents. For that, the team's own human annotation (12.4) is essential.

### 12.2 Baselines

| ID | Baseline | Purpose |
| --- | --- | --- |
| B0 | Greedy extractive (TF-IDF sentence selection) | Non-neural floor |
| B1 | Hybrid extract-then-abstract (embeddings, k-means, rank, rewrite) | Compare hybrid design |
| B2 | Uniform fixed-size chunking with map-reduce | Isolates section-aware chunking |
| B3 (optional) | Truncate to window then single pass | What naive systems do |

### 12.3 Experiments

| ID | Question | Independent variable | Dependent variables | Notes |
| --- | --- | --- | --- | --- |
| E1 | Is single-pass better than divide-and-conquer when the document fits? | Route A vs B (forced) on same docs | Faithfulness, coverage, ROUGE, latency | Use `gemini_full` |
| E2 | Where does divide-and-conquer start to cost faithfulness? | `tau` via simulated profiles | Faithfulness vs `tau` | Use `sim_8k/16k/32k` (Section 8.1) |
| E3 | Does faithfulness fall as merges accumulate? | Merge level in the reduce tree | Faithfulness per level | Needs deep trees: use small chunks or long docs |
| E4 | Does section-aware chunking help? | Section-aware vs uniform (B2), matched chunk size | Faithfulness, coverage | |
| E5 | Can the local verifier be trusted? | DeBERTa vs MiniCheck vs LLM judge | Agreement with human labels, perturbation behaviour | Includes 11.9 suite |

E3 caution: with 3,000-token chunks a 10k-token paper produces only about 4 chunks, so the reduce tree has 1 or 2 levels. Per-level analysis needs more levels, which means smaller chunks (for example 500 to 1,000 tokens) or genuinely long inputs (reports, books). Decide the E3 document source early.

### 12.4 Human annotation

Needed because no public human labels exist for long scientific summaries.

- Sample 30 documents from the gold set; for each, use one Route A and one Route B summary.
- Two annotators label each decomposed claim `supported / contradicted / unsupported` against the source, independently, using `eval/annotate.py` (a small Gradio or CSV tool).
- Report Cohen's kappa; adjudicate disagreements.
- Use these labels to compute verifier accuracy, precision, recall and F1 on the actual target domain (this feeds report Table 5.2).

### 12.5 Metrics

| Group | Metric | Library |
| --- | --- | --- |
| Primary | Claim faithfulness, coverage, compression ratio | own code |
| Comparison | ROUGE-1/2/L, BERTScore | `rouge-score`, `bert-score` |
| Validation | Spearman rho, Kendall tau vs SummEval ratings; precision/recall/F1 on AggreFact; confusion matrix | `scipy`, `scikit-learn` |
| Operational | Latency, API calls, tokens per document, cache hit rate | `llm_calls` table |

ROUGE and BERTScore are reported for comparability only and are not treated as evidence of faithfulness.

### 12.6 Experiment budget (plan before running)

Free-tier quotas are the bottleneck. Estimate before every run:

```
Route A calls  = docs x seeds
Route B calls  = docs x seeds x (chunks + merge_nodes)         # merge_nodes ~ chunks / (k-1)
Claim decomposition = local (no API)
Total API calls vs  daily cap (RPD) and per-minute caps in configs/models.yaml
```

Rules:

- Run a pilot on 20 to 50 documents first and measure real calls per document.
- Use the cache so a rerun costs nothing.
- If the daily cap is reached, the runner pauses and resumes the next day; do not split one experiment across different models.
- Use the local Qwen3-8B for bulk arms where quality is not the question being tested, and say so in the report.
- Three seeds apply to anything that samples; with temperature 0.2 expect small variance, so confirm on a pilot before paying for three seeds everywhere.

### 12.7 Run outputs

```
results/<experiment>/<run_id>/
├── manifest.json          # commit, config, prompt hashes, models, seeds, times
├── per_doc.jsonl          # one record per document and arm
├── claims.jsonl           # every claim, evidence, labels
├── llm_calls.jsonl
└── aggregate.csv          # mean and std over seeds
```

`eval/report.py` reads only these files to produce the tables and figures for report chapter 5: results table, verifier table, faithfulness vs `tau`, faithfulness per merge level, verifier P/R/F1 bars, and metric-vs-human scatter.

## 16. Risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Free-tier limits or terms change | Experiments stall | Limits in config; cache; pilot first; local fallback for bulk arms |
| Route B rarely triggers on real windows | E1 to E4 have nothing to compare | Simulated profiles (Section 8.1); long-document source for E3 |
| Claim decomposition errors | Faithfulness scores are biased | Measure decomposer accuracy; compare with a stronger decomposer on a subset |
| NLI domain shift to scientific text | Verifier misjudges claims | Tune thresholds on dev data; report accuracy on own annotations |
| GROBID fails on some PDFs | Missing structure | `structure_ok` flag; exclude and report the count |
| 12 GB VRAM limits | Large verifier or model will not fit | Start with Flan-T5-large MiniCheck and DeBERTa; quantise; Kaggle T4 for batches |
| Human annotation takes longer than planned | E5 and verifier table delayed | Start by week 2 of P8; cap at 30 documents; two annotators in parallel |
| Data contamination | Inflated scores | Gold set from recent papers; say so in report |
| Hosted demo cannot run GPU verification | Demo incomplete | Demo mode with precomputed examples plus a live mode for local use |
| Prompt drift between runs | Irreproducible results | Prompts frozen and hashed in the manifest |
| Team coordination | Merge conflicts, duplicated work | One module per owner; PRs; shared `schemas.py` changed only by PR |
